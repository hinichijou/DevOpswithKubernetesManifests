## Todo app

Configuration files and Kubernetes cluster running instructions for an application that displays a list of todos and a random image from `https://picsum.photos/1200`. Consists of a Next.js + React frontend, a Node.js + Hono backend and a PostgreSQL database which is used by the backend to store the todo data. The source code for the application can be found [here](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app)

First run a Kubernetes cluster. In chapter 5 of the course we move back to using a local cluster. For example with [k3d](https://github.com/k3d-io/k3d) you can create a cluster with `k3d cluster create -p 8081:80@loadbalancer -p 8080:81@loadbalancer --agents 2 --k3s-arg '--disable=traefik@server:*'`. Local port 8081 is opened to port 80 and 8080 to 81 in load balancer. `--disable=traefik@server:*` is required for traefik not to interfere with the Envoy and Istio installation. If the cluster already exists it can be started with `k3d cluster start`.

Check with `kubectl cluster-info` that your configuration is pointing to the local cluster. If it is not we can correct this by running `kubectl config get-contexts` to get the name of the context and set it with `kubectl config use-context *context-name*`.

The cluster uses a gateway resource which doesn't exist in a k3d cluster out of the box. Install the Envoy gateway using the instructions from the [envoy_gateway folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/5.7/services/envoy_gateway).

The cluster uses a gateway resource to handle inter-namespace routing from a single externally exposed port to different services. Apply the infra resources using the instructions from [infrastructure folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/5.7/infrastructure). This also creates the necessary namespace and persistent volumes. The todo application uses two namepaces: `project-staging` and `project-production`. There are separate persistent volumes created for production and staging environments.

The application uses [NATS](https://docs.nats.io/) for messaging. Install NATS with the instructions [in the nats service folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/5.7/services/nats).

The application uses SealedSecrets to decrypt sensitive files inside the cluster. Install with the instructions in the [sealed_secrets folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/5.7/services/sealed_secrets). If the cluster was just created [`sealed_secret_postgres_staging.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/resources/sealed_secret_postgres_staging.yaml) and [`sealed_secret_postgres_production.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/prod/resources/sealed_secret_postgres_production.yaml) should be re-encrypted and re-pushed to the repository as they can only be decrypted by the cluster that sealed them. More details about these files can be found further in the instructions.

To automate the deployment Argo CD can be added to the cluster using the instructions from [argocd service folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/services/argocd), also the application manifest located in that folder should be applied. `secret_discord_webhook_staging.yaml` and `secret_discord_webhook_prod.yaml` should be created and deployed to their respective namespaces before application deployment since they are not pushed to GitHub and is not part of the automated deployment. More details about these files can be found further in the instructions. Argo CD watches for manifest changes in the defined git repo folder and redeploys the application if necessary.

[push_image_changes_on_dispatch.yaml](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/.github/workflows/push_image_changes_on_dispatch.yaml) defines GitHub workflow triggered by the source code repository for updating the correct images to kustomization files. The same workflow handles the deployment for both the todo app and log output pingpong application. Argo CD is configured to watch for manifest changes to each application/environment combination kustomization file, any changes trigger a redeployment. [See readme](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/.github/workflows/README.md) for more detailed description.

To deploy manually use `kubectl apply -k .` in the [staging](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging) or [production](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/prod) folder, which creates the resources listed in the `kustomization.yaml` located in the folder. The services define how the used application ports of the frontend and backend applications are connected to cluster internal network ports. The route resources define how the cluster internal services match to routing paths while the gateway resource defines a point of access to the cluster at which traffic is routed. The todo frontend application and the todo backend application have externally exposed routes while the postgres database is not exposed externally. The frontend requests  `/todo` path of the backend service. The todo list get is requested by the frontend directly using the kubernetes cluster internal routing and the post request for a new todo and the put request for marking a todo done is done from the browser to the backend.

Since route resources don't support strategic merges it seemed more convenient to create separate route resources for different environments. To be able to access both the staging and production applications while they are deployed at the same time there are separate route resource files for [staging](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/resources) and [production](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/prod/resources). Staging is available at http://localhost:8080/todoapp-staging/ and production at http://localhost:8080/todoapp-prod/. For the Next.js frontend to work the [root path](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/todo_app_frontend/next.config.ts) of the application needs to be defined on build time in the Docker build context. The [staging](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/resources/route_backend_staging.yaml) and [production](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/prod/resources/route_backend_prod.yaml) backend application routes define a route rewriting rule where requests to the `/api` path are routed to the root path of the backend application, making the backend available at http://localhost:8080/todoapp-*environment-name*/api/.

[`persistentvolumeclaim_todoapp_prod.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/prod/patches/persistentvolumeclaim_todoapp_prod.yaml) and [`persistentvolumeclaim_todoapp_staging.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/patches/persistentvolumeclaim_todoapp_staging.yaml) request persistent volume resources to be used by the todoapp frontend to save the displayed image, the data written persists between application runs. Because the PersistentVolume gets claimed by a specific PersistentVolumeClaim deployment, if you remove the resources but want to use the same persistent volume to keep the data stored for a new deployment you should delete the `claimRef` entry from PV specs, so as new PVC can bind to it. This should make the PV Available. This can be done with bash command `kubectl patch pv todoapp-*environment here*-pv -p '{"spec":{"claimRef": null}}'`.

[`configmap_todoapp.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/configmap_todoapp.yaml) holds the environment variables for the todo application frontend and backend. See [backend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/backend/README.md) and [frontend readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/todo_app_frontend/README.md) for more information on what the meaning of each of the environment variables is.

 The backend saves the todo data to a Postgres database with persistent storage which is run as a single replica StatefulSet defined in [`statefulset_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/statefulset_postgres.yaml). The env values required for the configuration of the database and the connection between backend and database can be found in [`configmap_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/configmap_postgres.yaml). The configMapGenerator in [`kustomization.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/kustomization.yaml) creates a file resource for the database initialization based on the contents of the [`init_todo_db.sql`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/init_todo_db.sql) file. This file also defines the default todos displayed on the page. If deployed to a local cluster the setup should also contain a secret file  `secret_postgres.yaml` which is not in version control which has the name `secret-postgres-config` and defines the environment variable `POSTGRES_PASSWORD`. You can for example refer to the encrypted staging version of the file [`sealed_secret_postgres.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/resources/sealed_secret_postgres_staging.yaml) to see what kind of resource is expected.

 The [backend](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/backend) publishes a NATS message on `/todos` POST and PUT with the subject defined in [configmap_nats.yaml](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/configmap_nats.yaml). The broadcaster in turn subscribes to this subject. See the [broadcaster folder](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/broadcaster) and the [broadcaster readme](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/broadcaster/README.md) for the broadcaster implementation and an explanation of the environment variables. The broadcaster expects a file to which the [broadcaster deployment](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/deployment_broadcaster.yaml) refers with the name `secret-discord-webhook-config` which contains the value for the environment variable `EXTERNAL_SERVICE_URL`. `secret_discord_webhook_staging.yaml` has `EXTERNAL_SERVICE_URL` set to `""` which effectively results in the messages just being logged. `secret_discord_webhook_prod.yaml` has `EXTERNAL_SERVICE_URL` set to the actual course discord webhook. These need to be applied to the correct namespaces before deployment with `kubectl apply -f secret_discord_webhook_staging.yaml -n project-staging` and `kubectl apply -f secret_discord_webhook_prod.yaml -n project-production`.

[`wikipedia_todo_job.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/wikipedia_todo_job.yaml) defines a CronJob that sends a new todo post request to backend every hour with the content of "Read *random wikipedia link*". The random wikipedia link is obtained by sending a request to https://en.wikipedia.org/wiki/Special:Random. The job uses a Docker image that contains a single shell script, the contents of the image can be found from [`wikipedia_todo_job folder`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/wikipedia_todo_job).

[`db_backup_job.yaml`](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/base/manifests/db_backup_job.yaml) defines a CronJob that takes a backup of the postgres database every 24 hours and saves the result to Google Cloud Storage bucket. The job uses a Docker image that contains a single shell script, the contents of the image can be found from [`db_backup_job folder`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/db_backup_job). See [`db_backup_job readme`](https://github.com/hinichijou/DevOpswithKubernetes/tree/4.10/todo_app/db_backup_job/README.md) for more detailed explanation. The job is written to authenticate as a Google Cloud cluster internal job using Workload Identity Federation so the job doesn't work when running in a local cluster. The job has a [staging overlay](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/todo_app/overlays/staging/patches/db_backup_job_staging.yaml) with `suspend: true` meaning that the job isn't scheduled in the staging environment by default.

You can follow pod output logs with `kubectl logs -f *insert pod name here*`. You can use `kubectl get pods` to find out the pod name.

See the [monitoring folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/monitoring) and the [monitoring readme](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/monitoring/README.md) for instructions on how to run a monitoring setup for the deployment.

You can view the HTML page served from http://localhost:8080/todoapp-staging or http://localhost:8080/todoapp-prod. The frontend fetches a new image from https://picsum.photos/1200 every 10 minutes. The frontend writes the image to persistent storage so it persists between application restarts. Frontend reads said image from the persistent storage and displays it. The backend has get, post and put paths for todos at `/todos` which is accessable at http://localhost:8080/todoapp-staging/api/todos or http://localhost:8080/todoapp-prod/api/todos. The frontend has the functionality for displaying the todos, adding a new todo and marking a todo as done. The Wikipedia todo CronJob is scheduled to post a new todo with a random Wikipedia link every hour.

You can remove the resources applied with the kustomization file with `kubectl delete -k .`. This doesn't delete the postgres persistent volumes which are not directly created in the manifests. You can delete them by finding the names with `kubectl get pvc` and calling delete directly for the persistent volume claims. You can also delete all resources of certain type, for example `kubectl delete --all deployments` would delete all deployment resources in the current namespace. Deleting the whole namespace with `kubectl delete namespace project` will also delete all the resources in the namespace. The Argo CD application deletion also deletes deployment related resources. This can be done with `kubectl delete -f applications/applicationset_todo_app.yaml` in the [argocd service folder](https://github.com/hinichijou/DevOpswithKubernetesManifests/tree/4.10/services/argocd).

The cluster can be stopped with `k3d cluster stop` and started with `k3d cluster start`. The cluster can be deleted with `k3d cluster delete`.
